labrat: a GitLab API simulator

labrat is a single Rust binary that answers like GitLab CE 18.11 for merge requests and code review: REST, GraphQL, webhooks and git over HTTP, with everything stored in one SQLite file. This page explains how it is built, how its fidelity is checked against a real GitLab, and what that checking has found so far.

Architecture

Clients talk to labrat exactly as they would to GitLab: the same URLs, tokens, JSON shapes, headers, pagination and errors. Requests go through an axum router to services in labrat-core, which hold GitLab's business rules. One SQLite database holds the domain tables and the git objects. A background job queue stands in for Sidekiq, so asynchronous effects (mergeability checks, system notes, webhooks) happen after the request, as they do in GitLab.

labrat-git

A small git implementation over SQLite: loose objects, packfile parsing and generation for smart HTTP, tree diffs, three-way merges, rebases and squashes.

labrat-core

GitLab's services, re-derived from its source and from recordings: how an MR is created, refreshed on push, checked for mergeability, reviewed, approved and merged, and which notes, todos and webhooks each step produces.

labrat-api

REST endpoints and entities with GitLab's exact field order, a GraphQL executor with GitLab CE's schema, the request log and a review UI.

labrat (CLI)

Starts the server with a database path, the external URL and a configurable delay for background jobs.

Record and check

Fidelity is measured, not assumed. Each scenario in tests/conformance is a Rust test that issues API calls. In record mode it runs against the reference GitLab and writes a fixture. In check mode the same code runs against an in-process labrat and every response is compared with the fixture: status, the compared headers, the body and even key order. Ids, times, SHAs and tokens differ between runs, so both sides go through the same normalizer first.

The normalizer replaces each concrete id with a placeholder numbered by first appearance and kind (<mr:1>, <user:2>, <note:7>), so the two sides must agree on which object an id refers to, not on its value. It also handles SHAs, short SHAs, upload secrets, ids inside URLs and query strings, and run-specific names. Webhooks are captured by a local receiver and recorded as steps too, so payloads are compared field by field like any response.

Replaying time

Some GitLab behaviour depends on wall-clock time. The clearest case: a merge request is "touched" (its updated_at moved) by notes, labels or assignees at most once a minute. Whether a webhook's changes lists updated_at therefore depends on how long ago the MR last changed. GitLab takes seconds per step, while labrat replays a scenario in milliseconds.

So recordings store when each step was sent. On replay, the harness moves that labrat instance's clock forward before each step until at least as much time has passed as on GitLab. Each instance has its own clock, so scenarios still run in parallel.

Random walks

Hand-written scenarios test what someone thought to test. The random_walk* scenarios instead run a fixed-seed sequence of operations, 40 to 60 steps, by two users on one or two MRs. The operations include comments, threads, drafts, diff notes, suggestions, approvals, labels, reviewers, quick actions, pushes, commit statuses, rebases, merges and close/reopen. The seed makes every run issue the same requests, so a walk records like any other scenario. The hooks walks also compare every webhook delivery after each step.

Source audits

Some behaviour is hard to provoke through the API: a guard in a service, a throttle, a race between two workers. Cheap subagents read GitLab's source for one topic at a time and write a report with file:line references to docs/gitlab-ref/, for example on webhooks, REST parameter edge cases, GraphQL fields or MR timestamps. Each claim is then confirmed by a recording before labrat changes. Several claims turned out wrong, and the recording wins.

Coverage

Merge requests

Create, update, list filters and sorts, diffs and versions, commits, context commits, mergeability and detailed status, merge, auto-merge, scheduled merges, rebase, squash, merge refs, pipelines, time tracking, archived projects.

Review

Notes, threads, diff and image notes, suggestions, draft notes and review submission, approvals, reviewer states, requested changes, award emoji, todos, mentions, quick actions, system notes, resource events.

GraphQL

A custom executor that matches GitLab's validation and error messages, pagination and null propagation; MR, project, user, group, repository and pipeline fields; review mutations.

Webhooks and git

MR, note, emoji, push, pipeline and system hooks with GitLab's payloads and changes; branch filters; smart HTTP clone, fetch and push with refresh processing.

Out of scope by design: forks and cross-project MRs, CI runners and jobs, and issues. GitLab CE 18.11 is the target. Documented-versus-actual mismatches are listed in docs/discrepancies.md; the progress log is docs/LOG.md.

Running it

cargo run -p labrat -- --db labrat.sqlite --external-url http://localhost:8080

cargo test                                                  # check labrat against all recordings
cargo test -p labrat-conformance --test conformance random_walk   # some scenarios

LABRAT_RECORD=1 GITLAB_URL=… GITLAB_TOKEN=… \
  cargo test -p labrat-conformance --test conformance <name> -- --test-threads=1   # re-record
