## 1. Authentication

### 1.1 How a token is found

Entry: `API::APIGuard::HelperMethods#find_current_user!` (`lib/api/api_guard.rb:57-71`) is called lazily from
`API::Helpers#current_user` (`lib/api/helpers.rb:85-114`) via `initial_current_user` (`helpers.rb:935-946`).
Source order for a normal endpoint (`api_guard.rb:73-85`):

1. `deploy_token_from_request` (only if `route_setting :authentication, deploy_token_allowed`) - none of the
   users/groups/projects/members/PAT endpoints set it.
2. `find_user_from_bearer_token` = `find_user_from_job_bearer_token` (needs `job_token_allowed`) then
   `find_user_from_access_token` (`lib/gitlab/auth/auth_finders.rb:92-94,148-157`).
3. `find_user_from_job_token` (needs `route_setting :authentication, job_token_allowed: ...`; `auth_finders.rb:96-103`).
4. `user_from_warden` (session cookie; only for requests passing CSRF `verified_request?`; GET/HEAD always pass;
   2FA-required-but-not-set-up users are dropped; `api_guard.rb:154-171`).

Where the raw token string comes from (`auth_finders.rb:268-272`, `366-412`):

* `extract_personal_access_token` = `params[:private_token]` (query or body) || header `PRIVATE-TOKEN`
  (rack env `HTTP_PRIVATE_TOKEN`, header name is case-insensitive) || `parsed_oauth_token`.
* `parsed_oauth_token` (Doorkeeper, `config/initializers/doorkeeper.rb:107`): `params[:access_token]`, then
  `Authorization: Bearer <tok>` (regex `/^Bearer /i`), then `params[:bearer_token]`.
* If the extracted token starts with the PAT prefix (`glpat-` default; `Authn::Tokens::PersonalAccessToken.prefix?`,
  `lib/authn/tokens/personal_access_token.rb:6-14`, also matches instance-prefixed variants) the PAT table is
  queried directly (`PersonalAccessToken.find_by_token`, digest lookup). Otherwise OAuth (Doorkeeper
  `OauthAccessToken.by_token`) is tried first, then falls back to PAT lookup (so a non-`glpat-` PAT in a Bearer
  header still works).
* HTTP Basic is only honoured when `route_setting :authentication, basic_auth_personal_access_token: true`;
  not set on any endpoint in this document, so Basic auth is ignored (request is anonymous).
* Any path starting `/api/v4/internal/kubernetes/` never yields an access token (`auth_finders.rb:372`).

Unknown token: `PersonalAccessToken.find_by_token(...) || raise(UnauthorizedError)` (`auth_finders.rb:411`) ->
`initial_current_user` rescues `Gitlab::Auth::UnauthorizedError` and calls `unauthorized!`
(`helpers.rb:940-941`) -> **401 `{"message":"401 Unauthorized"}`**, *no* `WWW-Authenticate` header **[O]**
(same for a bad `Authorization: Bearer`, bad `private_token=` param **[O]**). `Gitlab::Auth::TokenNotFoundError` /
`MissingTokenError` are declared but never raised in this code path.

**Job tokens are silently skipped on these endpoints.** `find_personal_access_token` returns `nil` for a CI job token
(`Authn::Tokens::CiJobToken.prefix?`, `glcbt-...`) when the request path starts with `/api/`
(`auth_finders.rb:408`), and none of the users/groups/projects/members endpoints set `job_token_allowed`,
so a job token sent in `PRIVATE-TOKEN`, `Authorization: Bearer`, or `job_token=` yields an *anonymous* request
(no 401). Anonymous behaviour then follows the endpoint (public data or 401/403/404). `JOB-TOKEN` header and
`job_token` param are only read by `find_user_from_job_token`, which requires the route setting.

Token validation order (`app/services/access_token_validation_service.rb:18-36`), called with `scopes: []` at
authentication time (so only expiry/revocation/impersonation checked) and again from `current_user` with the
endpoint's registered scopes (`helpers.rb:94-95`):

1. `token.expired?` (`expires_at <= now`, `app/models/concerns/expirable.rb`) -> EXPIRED
2. `token.revoked?` -> REVOKED
3. scope check (skipped for `granular` tokens) -> INSUFFICIENT_SCOPE
4. impersonation token and `Gitlab.config.gitlab.impersonation_enabled` false -> IMPERSONATION_DISABLED

Because the first call passes no scopes, expiry/revocation errors fire for *any* request that evaluates
`current_user`, before scope checks. An endpoint that never evaluates `current_user` never validates the token.
A user for whom `user.can?(:access_api)` is false is rejected with
`forbidden!(<reason>)` (`api_guard.rb:63-65`) -> `{"message":"403 Forbidden - <reason>"}`; reasons from
`lib/gitlab/auth/user_access_denied_reason.rb:10-35`, e.g. `Your account has been blocked.` **[O]**,
`Your account has been deactivated by your administrator. Please log back in from a web browser to reactivate your account at <gitlab url>`,
`Your primary email address is not confirmed. Please check your inbox for the confirmation instructions. In case the link is expired, you can request a new confirmation email at <new_user_confirmation_url>`,
`Your account is pending approval from your administrator and hence blocked.`, `This action cannot be performed by internal users`,
`Your password expired. Please access GitLab from a web browser to update your password.`,
`You (@user) must accept the Terms of Service in order to perform this action. To accept these terms, please access GitLab from a web browser at <url>.`

### 1.2 Exact error responses for token problems

Handler `oauth2_bearer_token_error_handler` (`api_guard.rb:191-251`) builds `Rack::OAuth2::Server::Resource::Bearer::*`
errors (rack-oauth2 2.2.1). Body = JSON of non-blank `{error, error_description, error_uri[, scope]}`;
`Content-Type: application/json`. 401 responses add `WWW-Authenticate: Bearer realm="Protected by OAuth 2.0", error="invalid_token", error_description="<desc>"`
(realm is the gem default because the handler builds the error without a realm; the `'The API'` realm on the
middleware in `api_guard.rb:14` is not used here). 403 responses have **no** `WWW-Authenticate` (see FIXME at
`api_guard.rb:219-220`).

| Condition | Status | Body | WWW-Authenticate |
|---|---|---|---|
| Expired | 401 | `{"error":"invalid_token","error_description":"Token is expired. You can either do re-authorization or token refresh."}` | `Bearer realm="Protected by OAuth 2.0", error="invalid_token", error_description="Token is expired. You can either do re-authorization or token refresh."` |
| Revoked | 401 | `{"error":"invalid_token","error_description":"Token was revoked. You have to re-authorize from the user."}` | same pattern with that description (revoking via PAT API also triggers `revoke_token_family` only for `.../access_tokens/(\d+\|self)/rotate` paths, `auth_finders.rb:608-622`) |
| Impersonation disabled | 401 | `{"error":"invalid_token","error_description":"Token is an impersonation token but impersonation was disabled."}` | same pattern |
| Insufficient scope | 403 | `{"error":"insufficient_scope","error_description":"The request requires higher privileges than provided by the access token.","scope":"<space separated scope names>"}` **[O]** (`"scope":"sudo"`) | none |
| Unknown / garbage token, unknown PAT | 401 | `{"message":"401 Unauthorized"}` | none **[O]** |
| No credentials on an endpoint calling `authenticate!` | 401 | `{"message":"401 Unauthorized"}` | none **[O]** |
| Blocked/unconfirmed/deactivated user | 403 | `{"message":"403 Forbidden - <reason>"}` | none |

`scope` in insufficient-scope = the endpoint's registered scopes, in registration order, endpoint class first then
`API::API`'s, regardless of the per-scope `if:` condition (`api_guard.rb:103-115`). E.g. Users class:
`"read_user ai_workflows api read_api"`; Projects/Groups: `"ai_workflows api read_api"`; Members/PersonalAccessTokens
(no APIGuard include): `"api read_api"`. For the sudo check the list is just `"sudo"`.
Other rescued errors in this list (DPoP, language-server, granular) are irrelevant on a default instance
(`dpop_authentication` flag default false).

### 1.3 Scopes and which endpoints need which

Scope matching: token scopes must include *any* registered scope whose `if:` condition passes
(`access_token_validation_service.rb:38-56`, `lib/api/scope.rb:16-18`). Registered (`lib/api/api.rb:53-54`, applies to
every API class): `api` (all methods) and `read_api` (only `GET`/`HEAD`). Additional per class:

* `API::Users` (`lib/api/users.rb:9-12`): `read_user` for GET/HEAD (covers `/users/*` and `GET /user`, since `resource :user` is in the same class);
  `ai_workflows` for HEAD or `GET /api/v\d+/user$`.
* `API::Projects` (`projects.rb:16`), `API::Groups` (`groups.rb:14`): `ai_workflows` for GET/HEAD.
* `API::PersonalAccessTokens` (`/personal_access_tokens`, `/personal_access_tokens/:id`) has no extra scope: needs `api` or (GET) `read_api`.
* `API::PersonalAccessTokens::SelfInformation` (`GET|DELETE /personal_access_tokens/self`, `GET .../self/associations`):
  `allow_access_with_scope(Gitlab::Auth.all_available_scopes)` (`self_information.rb:267`) - any scope works, including DELETE.
* `read_repository`/`write_repository`/`read_registry`/... tokens are NOT accepted anywhere in this document.
* `sudo` scope is required when a Sudo is requested (1.4). `admin_mode` scope only matters when `admin_mode` setting is on (1.5).
* Valid scope names for PAT creation: `Gitlab::Auth.all_available_scopes` = `api read_api read_user create_runner manage_runner k8s_proxy self_rotate mcp mcp_orbit granular`
  + `read_repository write_repository` + registry scopes (only if `Gitlab.config.registry.enabled` / `dependency_proxy.enabled`:
  `read_registry write_registry`, `read_virtual_registry write_virtual_registry`) + `read_observability write_observability` + `ai_features`
  + admin scopes `sudo admin_mode read_service_ping` (`lib/gitlab/auth.rb:22-31,563-565,490-492`; admin scopes appended at 490-492).

Authorization levels used by endpoints (helpers `lib/api/helpers.rb:394-433`):
`authenticate!` -> 401 unless `current_user`; `authenticate_non_get!` (before filter on Users/Groups/Projects) -> 401 for any non-GET/HEAD without a user;
`authenticated_as_admin!` -> 401 if anonymous, else 403 `{"message":"403 Forbidden"}` unless `current_user.can_admin_all_resources?`;
`authorize!(ability, subject)` -> 403 `{"message":"403 Forbidden"}`.

### 1.4 Sudo

`sudo!` (`helpers.rb:949-972`), run on every `current_user` evaluation. Identifier = `params[:sudo]` || header `Sudo` (rack `HTTP_SUDO`).
In order:
1. no authenticated initial user -> `unauthorized!` (401 `{"message":"401 Unauthorized"}`).
2. initial user not `can_admin_all_resources?` -> 403 `{"message":"403 Forbidden - Must be admin to use sudo"}`.
3. no access token (session / job token only) -> 403 `{"message":"403 Forbidden - Must be authenticated using an OAuth or personal access token to use sudo"}`.
4. token lacks `sudo` scope (expiry/revocation re-checked) -> 403 insufficient_scope body with `"scope":"sudo"` **[O]**.
5. `find_user(identifier)` = `UserFinder#find_by_id_or_username` (all-digit string -> id, else username, case-insensitive) not found -> 404 `{"message":"404 User with ID or username '<identifier>' Not Found"}`.
After a successful sudo, `current_user` is the sudoed user and per-endpoint scope validation is skipped (`helpers.rb:94`: `unless sudo?`).
Sudo as a blocked user is not special-cased in `sudo!`.

### 1.5 admin_mode setting (default off)

`application_settings.admin_mode` default false (`db/structure.sql` column `admin_mode boolean DEFAULT false NOT NULL`).
Off: `BasePolicy` condition `admin` is just `user.admin?` (`app/policies/base_policy.rb`, the `condition(:admin)` block);
`bypass_session_for_admin_mode?` is false (`api_guard.rb:93-98`); the `admin_mode` token scope has no effect; an admin PAT with
only `api` scope can do all admin things. On: admin abilities need an active admin-mode session or a token with scope `admin_mode`
(token validity checked via `RequestAuthenticator#valid_access_token?(scopes: [:admin_mode])`); `owns_organization?` also checks it.
`User#can_admin_all_resources?` = `can?(:admin_all_resources)` (`user.rb:2603`), enabled by `rule { admin }` in BasePolicy.
Admin gets implicit OWNER everywhere: `Group#max_member_access_for_user` returns OWNER for `can_admin_all_resources?` (`group.rb:954-963`).

## 2. Common API behavior

### 2.1 Error body formats

All JSON, `Content-Type: application/json`. Two distinct shapes:

* **`{"message": ...}`** from `render_api_error!` (`lib/api/helpers.rb:676-685`) - all helper errors:
  * `not_found!(res=nil)` -> 404 `"404 <res> Not Found"` or `"404 Not Found"` (`helpers.rb:593-598`). e.g. `404 Project Not Found`, `404 Group Not Found`, `404 User Not Found` **[O]**.
  * `forbidden!(reason=nil)` -> 403 `"403 Forbidden"` or `"403 Forbidden - <reason>"` (`helpers.rb:581-583,670-674`).
  * `bad_request!(reason=nil)` -> 400 `"400 Bad request"` / `"400 Bad request - <reason>"` (note lowercase "request"). `bad_request_missing_attribute!(a)` -> `"400 Bad request - \"a\" not given"`.
  * `unauthorized!` -> 401 `"401 Unauthorized"` / `"401 Unauthorized - <reason>"`.
  * `not_allowed!` 405 `"405 Method Not Allowed"`; `conflict!` 409 `"409 Conflict"` (or custom string); `unprocessable_entity!` 422; `file_too_large!` 413; `service_unavailable!` 503;
    `too_many_requests!` 429 (+`Retry-After`); `not_modified!` 304; `no_content!` 204 (`"204 No Content"`, body dropped by Rack); `created!`; `accepted!` 202 -> body `{"message":"202 Accepted"}`.
  * `render_api_error!("text", status)` for custom strings, e.g. `{"message":"Username has already been taken"}` (409).
* **`{"error": "..."}`** from Grape itself: parameter validation, unknown route, `error!(string)` calls:
  * unknown route anywhere (`api.rb:428-430`) and route-requirement mismatches (e.g. `/users/abc` because `id: /[0-9]*/`) -> 404 `{"error":"404 Not Found"}` **[O]**.
  * validation errors via `rescue_from Grape::Exceptions::Base` (`api.rb:159-161`) -> 400 `{"error":"<msg>"}`.
* **`rescue_from` fixed bodies** (`api.rb:130-190`): `Gitlab::Access::AccessDeniedError` -> 403 `{"message":"403 Forbidden"}`;
  `ActiveRecord::RecordNotFound` -> 404 `{"message":"404 Not found"}` (lowercase "found"; used by `find_by!` in members endpoints) **[O]**;
  stale object / lock failure -> 409 `{"message":"409 Conflict: Resource lock"}`; `MovedPermanentlyError` -> 301 with `Location` and plain-text body
  `This resource has been moved permanently to <url>`; rate limit (`RateLimitedService::RateLimitedError`) -> 429 `{"message":{"error":"<msg>"}}`;
  `:all` -> 500 `{"message":"500 Internal Server Error"}`.
* `error!(Array/Hash, status)`: Hash -> as-is JSON; Array/String -> wrapped `{"error": x}` (e.g. project limit: 403 `{"error":["You've reached your limit of N projects created. Contact your GitLab administrator."]}`, `projects.rb:420-422`).

**Validation errors from models** (`render_validation_error!`, `helpers.rb:656-668`): 400 `{"message": <errors.messages hash>}`, keys are attribute names
(symbols as strings), values arrays of message strings, e.g. `{"message":{"username":["admin is a reserved name"]}}` **[O]**.
For several models, `messages` (Hash) of each are `join(" ")`-ed into one String (Ruby `Hash#to_s`) - only when `models.size > 1`; not used by any endpoint here.
Users API remaps `user_detail.bio` errors to `bio` (`lib/api/helpers/users_helpers.rb:17-26`).

**Group create errors are different**: `render_api_error!("Failed to save group #{group.errors.messages}", 400)` (`groups.rb:319`) - the message is a
Ruby `Hash#inspect` string with `{:path=>["has already been taken"]}` syntax (Ruby <=3.3 style, `:sym=>[...]`) **[O]**.
Group transfer errors: `"Failed to transfer project #{project.errors.messages}"`.

### 2.2 Grape parameter validation messages

Joined with `", "` per validator, in declaration order of validators; the whole is one string in `{"error": ...}`:

* missing required: `name is missing` ; multiple: `password, reset_password, force_random_password are missing, at least one parameter must be provided, name is missing` (`at_least_one_of` message then `requires` message) **[O]** (POST /users with only email+username).
* `at_least_one_of`: `<a>, <b> are missing, at least one parameter must be provided` **[O]** (`POST /projects` with neither: `name, path are missing, at least one parameter must be provided`; `PUT /projects/:id` with nothing lists all ~100 params in `Helpers::ProjectsHelpers.update_params_at_least_one_of` order **[O]**).
* `mutually_exclusive`: `<a>, <b> are mutually exclusive`. `all_or_none_of`: `<a>, <b> provide all or none of parameters`.
* bad enum: `visibility does not have a valid value` **[O]**; `order_by does not have a valid value` **[O]**. `except_values`: `per_page has a value not allowed` (per_page=0) **[O]**.
* type coercion: `per_page is invalid` **[O]**, `created_after is invalid`.
* Missing `values:`-constrained array element etc. same pattern. Nested: `container_expiration_policy_attributes[cadence] is invalid`.
Params in query string and body (form or JSON) are merged by Grape; booleans accept `true/false/1/0/t/f/yes/no/on/off`-style strings via Grape Boolean coercion.

### 2.3 404 vs 403 for invisible resources

* Groups: `find_group!` (`helpers.rb:258-277`): unreadable -> `404 Group Not Found` (anonymous too; `authenticate_non_public?` only on routes with that setting - none here).
* Projects: `find_project!` (`helpers.rb:179-200`): no such project -> 404 `404 Project Not Found`; exists but `can?(:read_project)` false -> same 404 (job-token users get 403 with a specific message, N/A). Archived/deletion-scheduled projects still readable.
* Users: `GET /users/:id` anonymous -> 403 `403 Forbidden - Not authorized!`; unknown or `!can?(:read_user)` -> 404 `404 User Not Found`.
* Members: group/project found first (404 if invisible), then `authorize! :read_group_member|:read_project_member` -> 403 `403 Forbidden`; member not in source -> 404 `404 Not found` (RecordNotFound), whereas a missing *user* on `POST /members` -> `404 User Not Found`.
* Write endpoints on a visible resource lacking permission -> 403 `403 Forbidden` (e.g. PUT project needs `admin_project`).
* Routes needing auth that get anonymous: 401 `401 Unauthorized`. `GET /users` anonymous without `username` -> 403 `403 Forbidden - Not authorized to access /api/v4/users` **[O]**.

### 2.4 `:id` resolution

* Project id (`helpers.rb:161-171`): value matching `/^-?\d+$/` (Integer or numeric string) -> `find_by(id:)`; else if it contains `/` -> `Project.find_by_full_path(id, follow_redirects: true)`; else (no slash, non-numeric, e.g. `demo`) -> `nil` -> 404. Scope `Project.without_deleted.not_hidden`. The slash must be URL-encoded (`%2F`); route requirement `id: [^/]+` (`api.rb:13`), a raw slash does not match -> `{"error":"404 Not Found"}`.
  Full-path lookup is **case-insensitive** (`Routable.find_by_full_path`: exact `Route` match, then `iwhere` fallback, then `RedirectRoute`; `routable.rb:28-40`) **[O]** `MAIN%2FDEMO` -> 200.
  If matched via redirect route or different case (`project_moved?`, `helpers.rb:1083-1089`: id is a String containing `/`, `project.full_path.casecmp?(id)` false, `params[:id] == id`): GET -> 301 `Location: <gitlab.url>/api/v4/projects/<numeric id>[ext][?query]` (`url_with_project_id`, `1091-1098`), body plain text `This resource has been moved permanently to <url>`; non-GET -> 405 `{"message":"Non GET methods are not allowed for moved projects"}`. Case-only differences are NOT "moved" (casecmp? passes).
* Group id (`helpers.rb:247-256`): numeric (`/^-?\d+$/`) -> id; else `Group.find_by_full_path(id)` (case-insensitive; **no** redirect-route following -> a renamed old group path is 404). A group whose path is all digits can only be addressed by full path with a slash or by id. `Group.all` scope (includes groups pending deletion).
* User id in `/users/:id...`: Grape `requires :id, type: Integer` plus route requirement `/[0-9]*/` (`users.rb:31`); `/users/:user_id/{status,keys,project_deploy_keys}` and `/users/:user_id/projects` accept `String` id-or-username (`API::USER_REQUIREMENTS`, `api.rb:15`): digits -> id else username, case-insensitive (`UserFinder#find_by_id_or_username`).
* Members/`id` param (`members.rb:19-22`): `type: String`, `NAMESPACE_OR_PROJECT_REQUIREMENTS`, resolved with `find_group!`/`find_project!`.

### 2.5 Offset pagination

`optional :page, Integer, default 1` and `optional :per_page, Integer, default 20, except_values [0]` (`lib/api/pagination_params.rb:115-119`).
Implementation `Gitlab::Pagination::OffsetPagination` (`lib/gitlab/pagination/offset_pagination.rb`) + Kaminari 1.2.2 (`config/initializers/kaminari_config.rb`: default 20, **max_per_page 100**).
* `per_page` > 100 is silently clamped to 100 (no error); negative `per_page` is ignored by Kaminari (20 used); `page` < 1 behaves as page 1; `per_page=0` -> 400 `per_page has a value not allowed`. (`only_positive_pagination_values` flag default off, `pagination_params.rb:121-139`.)
* Default order if the relation has none: `ORDER BY id ASC` (`offset_pagination.rb:50-58`); most list endpoints set their own order.
* Headers (`lib/gitlab/pagination/offset_header_builder.rb:133-175`), always: `X-Per-Page`, `X-Page`, `X-Next-Page` (empty string if none), `X-Prev-Page` (empty if none), `Link`. Plus `X-Total` and `X-Total-Pages` unless `exclude_total_headers`, or count is limited: when the relation has more than **10,000** rows (`MAX_COUNT_LIMIT`, `config/initializers/kaminari_active_record_relation_methods_with_limit.rb:6`) it uses `without_count` and then **omits `X-Total`, `X-Total-Pages` and the `rel="last"` link**; `X-Next-Page` is then derived by fetching one extra row. `X-Total-Pages` is at least 1 (empty result -> `X-Total: 0`, `X-Total-Pages: 1`).
* `Link` format: `<URL>; rel="prev"`, `<URL>; rel="next"` (each only if present), then `<URL>; rel="first"`, then `<URL>; rel="last"` (unless count omitted), joined by `", "`. Order: prev, next, first, last **[O]**. If no next page, only first/last **[O]**.
  URL = request URL with scheme/host/port forced to `Gitlab.config.gitlab.host/port` (port elided by URI when default) and `uri.query = params.merge(page: N, per_page: per_page).to_query`, where `params` is the **entire Grape params hash**: all request params (including unknown ones like `foo=bar` and path params like `id=2`), plus every declared param's default (`order_by=created_at`, `sort=desc`, `simple=false`, `statistics=false`, `owned=false`, `with_custom_attributes=false`,), keys sorted alphabetically by `Hash#to_query`, values escaped. Example **[O]**:
  `<http://localhost:8929/api/v4/projects?foo=bar&imported=false&membership=false&order_by=created_at&owned=false&page=1&per_page=2&simple=true&sort=desc&starred=false&statistics=false&with_custom_attributes=false&with_issues_enabled=false&with_merge_requests_enabled=false>; rel="first", <...page=1...>; rel="last"`
  and `GET /groups/2/members` -> `<http://localhost:8929/api/v4/groups/2/members?id=2&page=1&per_page=20>; rel="first", ...; rel="last"` **[O]**. Declared params with no default and not supplied (e.g. `search`, `archived`, `visibility`) are absent from the query.
* Other response headers on GET 200: weak `Etag` (Rack::ETag; `If-None-Match` -> 304), `Cache-Control: max-age=0, private, must-revalidate`; errors `Cache-Control: no-cache`; plus `X-Frame-Options: SAMEORIGIN`, `X-Content-Type-Options: nosniff`, `X-Gitlab-Meta: {"correlation_id":"...","version":"1"}`, `X-Request-Id`, `X-Runtime`, `Referrer-Policy` (`api.rb:65-74`).
* Offset cap: `paginate_with_strategies` (used by `GET /users`, `GET /projects`, anonymous `GET /groups`) rejects offset requests beyond `offset_pagination_limit` (plan limit, default **50000**, `db/structure.sql` plan_limits) for `Group` and `User` relations (always enforced) and `Project` (only anonymous + flag `enforce_projects_pagination_limit`, default off): 405 `{"error":"Offset pagination has a maximum allowed offset of 50000 for requests that return objects of type User. Remaining records can be retrieved using keyset pagination."}` when `page*per_page > 50000` (`pagination_strategies.rb:60-73,91-93`, `cursor_based_keyset.rb:36,47-57`). Requests using plain `paginate` (groups for logged-in users, members, PATs) have no cap.

### 2.6 Keyset pagination

Enabled by `pagination=keyset` (`pagination_strategies.rb:83-85`). Only endpoints calling `paginate_with_strategies`:
* **Projects** (`GET /projects`, `/users/:id/projects`, ...; `present_projects`, `projects.rb:228` passes `use_cursor: false`): classic keyset (`Gitlab::Pagination::Keyset`, `keyset.rb`). Available only if the order is exactly `id` (i.e. `order_by=id` and `sort` asc/desc; default sort for keyset is desc; `request_context.rb:9,36-45`) - otherwise 405 `{"error":"Keyset pagination is not yet available for this type of request"}`. `per_page` clamped 1..100 (`<=0` -> 20). Response: only a `Link: <...>; rel="next"` header (no X-Total, X-Page etc.) whose query = request params merged with `id_after=<last id>` (asc) or `id_before=<last id>` (desc) (`request_context.rb:58-67`); no header when the page is empty. Filters `id_after`/`id_before` are real param filters (`projects.rb:185-186`).
* **Users** (`GET /users`, `users.rb:242`) and **Groups** (only the *anonymous* branch of `GET /groups`, `groups.rb:159-173`; logged-in users use plain `paginate` so `pagination=keyset` is ignored): cursor-based (`CursorPager`). Supported orderings: `User.supported_keyset_orderings` = `id|name|username|created_at|updated_at` x `asc|desc` (`user.rb:803-811`); `Group` only `name asc` (`group.rb:41-43`); `order_by`/`sort` default `id`/`desc` in the cursor context, but groups list defaults `order_by=name,sort=asc`. Param `cursor`. Headers: `X-Next-Cursor`, `X-Prev-Cursor` (when present) and `Link: <...&cursor=XYZ>; rel="next"` (`cursor_based_request_context.rb:26-31`, `keyset/header_builder.rb`). Unsupported order -> the 405 error above.

## 4. Endpoints

Status code defaults: Grape `post` -> **201** unless `status` set; `get/put/delete` -> 200 (`delete` with `destroy_conditionally!` -> 204 no body).
`destroy_conditionally!` (`helpers.rb:51-64`) honours `If-Unmodified-Since` (412 `{"message":"412 Precondition Failed"}` if resource `updated_at` is newer), sets 204, then runs the block.
All user/group/project mutating endpoints require auth (`authenticate_non_get!` 401).

### 4.1 Users (`lib/api/users.rb`)

* **GET /user** (`1211-1226`): any authenticated; entity per 3.1. 401 if anonymous.
* **GET /users** (`172-243`): anonymous allowed only with `username` param (else 403 `Not authorized to access /api/v4/users`); also 403 for anonymous when `restricted_visibility_levels` include public. Params: `username, extern_uid, public_email, provider, search, active, humans, external, blocked, created_after, created_before, without_projects, without_project_bots, admins, two_factor, exclude_active, exclude_external, exclude_humans, exclude_internal, order_by (id|name|username|created_at|updated_at), sort (asc|desc), with_custom_attributes, page, per_page, pagination` (booleans default false). `extern_uid+provider` is admin-only (`authenticated_as_admin!`; `all_or_none_of`). ## 7. Permission model essentials

* Access levels (`lib/gitlab/access.rb:12-21`): NO_ACCESS 0, MINIMAL_ACCESS 5, GUEST 10, **PLANNER 15**, REPORTER 20, SECURITY_MANAGER 25 (only if env `GITLAB_SECURITY_MANAGER_ROLE` true; default off, so 25 is invalid), DEVELOPER 30, MAINTAINER 40, OWNER 50, ADMIN 60 (internal). Valid values for `access_level`/`min_access_level` params: `[10,15,20,30,40,50]` (`all_values`). Planner is non-hierarchical: `planner` condition is `access_level == 15` exactly; it gets issue/epic/work-item planning rights but is not "greater than Guest" for every ability (`group_policy.rb` conditions; `Gitlab::Access.level_encompasses?` special-cases PLANNER and SECURITY_MANAGER: assignable only by OWNER or an equal role).
* Roles->abilities come from `config/authz/roles/*.yml` (owner inherits maintainer + planner + security_manager). Relevant: group `admin_group`, `remove_group`, `create_subgroup`, `admin_group_member`, `invite_group_members`, `archive_group`, `change_group` -> **Owner only**; project `remove_project`, `change_visibility_level`, `archive_project`, `manage_owners`, `destroy_*` -> Owner; project `admin_project`, `rename_project`, `admin_project_member`, `admin_runners` -> Maintainer; `read_project`, `read_project_member` -> Guest (and anonymous for public projects).
* Membership inheritance: a user's group access = max over the group and its ancestors' direct memberships (`Group#max_member_access`, uses `traversal_ids`); project access = max(direct project member, group access from the project's group & ancestors, shared-group links capped by link `group_access`). Subgroup membership may not be lower than inherited (model error above). Admin: implicit OWNER on groups via `max_member_access_for_user`; for projects admin abilities come from `rule { admin }`.
* Visibility (`Gitlab::VisibilityLevel`: private 0, internal 10, public 20; `lib/gitlab/visibility_level.rb`): public -> anyone (even anonymous unless instance `restricted_visibility_levels` includes public: then `read_user`, user list denied to anonymous); internal -> any logged-in non-external user; private -> members/admins. `levels_for_user`: anonymous `[20]`, external `[20]`, admin `[0,10,20]`, regular `[10,20]` (+private via membership). `GroupPolicy`: `read_group` for members, public groups, internal groups for logged-in non-external users, admins, and users who have access to any project inside the group (`has_projects`). Read of a *private* group's member list requires membership (`can_read_group_member?`). Project `read_project`: public project (logged-in or anonymous... `public_project` grants `public_access`), internal (`internal_access`: logged in, non-external), or team member (guest+), via group, admin. A project in a private group stays private regardless of its own visibility; its visibility cannot exceed the namespace's.
* Blocked/deactivated/unconfirmed users cannot use the API (403 with reason, 1.1). Internal users (ghost, bots) likewise.
* Who can create projects in a group (`group_policy.rb:~304-310`, `group.rb:1018,570-575`): `project_creation_level` (nil -> instance `default_project_creation`, default 2=developer): `noone`(0) nobody (even owner; admin can via `rule { admin }.enable :create_projects`? - `create_projects_disabled` prevents unless admin, `prevent_project_creation?` returns false for admins except NO_ONE), `owner`(4) owners, `maintainer`(1) maintainers+, `developer`(2) developers+, `administrator`(3) only admins. Also prevented if no visibility level is allowed (restricted levels). In the user's own namespace: `projects_limit` > personal projects count and `allow_project_creation_for_guest_and_below` (setting, default true) / role > guest.
* Subgroup creation: Owner always; Maintainer if group `subgroup_creation_level == maintainer` (default 1 = maintainer) (`group_policy.rb:290` rule `maintainer & maintainer_can_create_group` -> `create_subgroup`; the owner role grants it directly); top-level groups need `create_group` (user attr `can_create_group` + not blocked from creating).
* Adding members: group: Owner (`admin_group_member`) - **not Maintainer**; project: Maintainer+ (`admin_project_member`); cannot grant above own level; Owner (50) on projects needs `manage_owners`; Planner (15) assignable only by Owner (or an existing Planner). Updating/removing: `update_*_member`/`destroy_*_member` are granted to holders of `admin_*_member` (not for project bots, which use `destroy_project_bot_member`) and a member may always remove themself (`destroy_*_member` via `target_is_self`); last group owner and personal-namespace holder cannot be changed/removed.
* Deleting groups/projects: Owner (or admin); `remove_project` is additionally removed from Owners when instance `default_project_deletion_protection` is on (`app/policies/base_policy.rb:80-84`).

## 8. Edge cases (easy to get wrong)

1. **`DELETE /users/:id` can delete the caller** (no self-check) and returns 204 immediately; the user is hard-gone within seconds (token invalid, personal namespace and projects removed, group/MR contributions re-attributed to Ghost unless `hard_delete`). During the window the user is `blocked`, so requests get `403 {"message":"403 Forbidden - Your account has been blocked."}` **[O]**. `POST /users/:id/block` on yourself is rejected (403), delete is not.
2. `Link` header contents are every declared param with defaults + every unknown param + path params, sorted by key (2.5). `X-Next-Page`/`X-Prev-Page` are present-but-empty strings, not absent. `X-Total` disappears above 10,000 rows. `per_page` > 100 silently becomes 100; `per_page=0` is a 400.
3. Two error JSON shapes: `{"message":...}` (helpers, ActiveRecord) vs `{"error":...}` (Grape validation, unknown route, route-requirement mismatch, `error!(String)`). `/users/abc` is `{"error":"404 Not Found"}`, `/users/9999` is `{"message":"404 User Not Found"}`. `find_by!` misses are `{"message":"404 Not found"}` (lowercase f, no resource word).
4. Unknown / bad token => plain `401 Unauthorized` without `WWW-Authenticate`; expired/revoked => 401 *with* OAuth-style `error`/`error_description` and `WWW-Authenticate`; wrong scope => 403 `insufficient_scope` JSON with a `scope` list (all of the endpoint's scopes, incl. ones whose `if:` would not apply). CI job tokens sent as PATs are ignored (anonymous), not rejected.
5. Token validity is only checked when `current_user` is evaluated; scopes are re-checked per endpoint after sudo is processed (sudo as admin skips endpoint scope checks entirely, only `sudo` scope required).
6. Project lookup by path is case-insensitive and follows redirect routes: renamed paths answer **301** to the numeric-id URL for GET (plain-text body `This resource has been moved permanently to <abs url>`), **405** for other verbs; different case alone does not redirect. Group lookup is case-insensitive but does **not** follow redirects (404). A path without `/` that isn't numeric never matches a project (404).
7. `GET /projects/:id` anonymous returns the `ProjectDetails` shape (no `_links`, no CI fields, no `permissions`); authenticated returns `ProjectWithAccess`. `POST/PUT /projects` responses never contain `permissions`. Admin who is not a member gets `permissions.project_access:null, group_access:null`.
8. `GET /projects` default sort is `created_at desc` implemented as `id desc`; for other sort keys the tie-breaker `id` follows the **same direction** as `sort` (`id <sort>`), not always asc. User list default is `id desc`; group list default is `name asc, id asc`; member lists `id asc`; PAT lists `id asc`.
9. Ordinary users' `GET /groups` returns only groups they belong to (plus ancestors) unless `all_available=true`; admins get everything; anonymous gets public groups. `owned`/`min_access_level` override `all_available`.
10. Keyset pagination: projects need `order_by=id`; groups only for anonymous callers (authenticated groups list silently ignores `pagination=keyset`); users/groups use opaque `cursor`; projects use `id_before`/`id_after` in the `Link: rel="next"` URL.
11. Deleting a group/project in 18.11 is **always** a soft delete via MarkForDeletion (202), with `-deletion_scheduled-<id>` suffix on name and path (path change creates a redirect route; so old path 301s for projects), 30-day adjourned period, `marked_for_deletion_on/at` populated in entities; permanent deletion needs `permanently_remove=true` + `full_path` and is allowed only for already-marked items (groups: only subgroups). Repeating DELETE on a marked resource returns 400 `Group|Project has already been marked for deletion`.
12. Visibility silently clamps on project creation (private group + `visibility=public` => private, 201), but raises a validation error on update (`New visibility level not allowed!` / `<level> is not allowed in a <ns level> namespace.`).
13. Project create/rename errors repeat messages under `project_namespace.name|path`, `name`, `path` keys (all three for duplicates). Group create errors are a stringified Ruby hash inside `message` (`Failed to save group {:path=>["has already been taken"]}`). Group create with HTML in name returns both the HTML-safety and format messages for `name` and, for a reserved path, `"<path> is a reserved name"`.
14. `POST /users`: 409 (not 400) for taken email/username - checked *after* failed save, email first; reserved username is 400. `organization` field is ignored on create. Admin-created users are unconfirmed unless `skip_confirmation`. Password for non-reset users is required unless `reset_password`/`force_random_password`.
15. `POST /users/:id/personal_access_tokens`: missing `expires_at` is auto-filled (365 days) when expiry is required (default), while `impersonation_tokens` requires `expires_at` explicitly (400 `can't be blank`). Valid-scope enum errors are Grape `scopes does not have a valid value` for PAT but model `can only contain available scopes` for impersonation tokens. Token plaintext is returned only on creation.
16. `GET /personal_access_tokens/:id`: non-admins get **401** (not 404/403) for anything they cannot read, including nonexistent ids; admins get 404. `GET /personal_access_tokens` for non-admins excludes impersonation tokens and ignores `user_id` (401 if it points to someone else).
17. Members: `POST` returns 409 `Member already exists` for any direct membership (incl. pending requests); for a user who only has inherited access it creates a direct row (400 if lower than inherited). Expired memberships are still listed until the purge worker deletes them. `GET .../members` excludes inherited members, `GET .../members/all` includes them and deduplicates to the highest level. Blocked users still appear in member lists. `query` replaces default ordering with search-rank ordering. Removing yourself is permitted at any level (except last owner).
18. Group Maintainers cannot add members (Owner only), but project Maintainers can; Owner on a project can only be assigned/removed by project owners/admins; Planner/Security Manager roles are not covered by the "<= your level" rule.
19. Boolean params default `false` in many lists; `declared_params(include_missing: true)` includes them in finder params but finders treat false as "no filter" (e.g. `active=false` does not mean "inactive users").
20. `admin_mode` is off by default so `admin` PAT scopes need no `admin_mode`; if turned on, admin-only endpoints return `403 Forbidden` for admin PATs without the `admin_mode` scope.
21. `render_validation_error!` is only used when an errors object exists; Ruby `Hash#inspect` formatting (`{:key=>[...]}`) must be reproduced exactly for group-create errors; Grape string errors sort validators in declaration order and join with `", "`.
